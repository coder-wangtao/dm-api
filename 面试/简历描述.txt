DamaoAPI｜本地大模型 API 网关（桌面端 + 无头服务）

独立设计并实现一套运行在本机的大模型网关。下游按 OpenAI 兼容协议接入（Chat Completions、Responses、Embeddings、Images、Audio、Models），上游对接 Moonshot（Kimi）、OpenAI、Anthropic、Ollama 等多家供应商。网关负责鉴权、按模型选路、协议转换、失败转移和用量记录，并可将网关地址、密钥和模型一键写入 Codex、Claude Code、Gemini CLI 等客户端配置。同时提供 Tauri 桌面窗口和可单独部署的无头 Web 管理端。

技术栈

桌面端：Tauri 2、Rust、WebView2；系统能力使用 tauri-plugin-dialog / opener / shell / clipboard / notification / autostart
前端：React 19、TypeScript、Vite 8、Tailwind CSS 4、React Router 7、Zustand；Markdown 渲染使用 react-markdown、remark-gfm、rehype-sanitize
后端：Rust 2021、Tokio、Axum 0.8、Tower / tower-http、reqwest、async-trait、Serde / serde_json
存储与配置：SQLite（sqlx 0.8）、toml / toml_edit（读写 Codex 等 TOML 配置）、tauri-plugin-store
安全：API Key 鉴权与配额、Argon2 管理端密码、OAuth2（上游账号登录）
可观测：tracing、tracing-subscriber、tracing-appender，请求 ID 贯穿转发链路
协议与转换：OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Ollama /api/chat；SSE 流式桥接；Responses→Chat、Chat→Messages 编解码
知识库：pdf-extract、pdfium-render、tree-sitter（TypeScript / JavaScript / Python / Rust / Go / Java）、tiktoken-rs 做 token 估算
主要工作

实现本地网关进程（默认 127.0.0.1:8777），统一暴露 /v1/chat/completions、/v1/responses、/v1/embeddings、/v1/models 等接口，用网关 API Key 做鉴权，再按渠道密钥访问上游。
设计多渠道路由：渠道启用状态、模型列表命中、模型映射（来源名→上游模型名）、空模型列表通配、优先级与权重；没有候选渠道时返回明确的 503，而不是打到错误上游。
完成 Codex 所需的 Responses→Chat Completions 转换。兼容 Codex 固定携带的 text.verbosity、纯文本 format、reasoning.effort，以及空的 developer/system 消息，避免 Moonshot 等上游返回 400；json_object / json_schema 映射为 Chat 的 response_format。
支持 Anthropic Messages 与 OpenAI SSE 互转，使下游保持 OpenAI 形态，上游仍可走 Claude 或 Ollama 原生接口。
实现客户端一键接入：用 toml_edit 改写 ~/.codex/config.toml（model_provider、base_url、wire_api=responses、experimental_bearer_token），并为 Claude Code、Gemini CLI 等写入各自配置；保留原始配置备份，可恢复。
提供渠道连通性测试、模型预设（含 Moonshot/Kimi）、API Key 配额和允许/拒绝模型列表。
桌面端与无头模式共用同一套 Rust 核心：桌面用 Tauri 命令，Web 管理端通过 HTTP invoke 复用同一前端页面。
知识库侧支持 PDF 解析与页面渲染、多语言 tree-sitter 代码切分，以及在上游未返回 usage 时用 tiktoken 估算 token。

凭证检测
检测原理：利用各家密钥的已知前缀模式做启发式匹配。这是业界标准做法（GitHub Secret Scanning、truffleHog 都是这个思路），误报率低、速度快（无需正则回溯）。
事先知道某些类型的密钥通常以什么字符串开头，然后通过检查字符串的开头特征，来判断它是否可能是一个敏感凭证。

Unicode 隐写检测
Unicode 特殊字符检测器，主要用于检测文本中隐藏的、肉眼不容易发现的特殊字符，防止攻击者利用这些字符进行文本混淆、
恶意代码隐藏或 AI 提示词攻击。

网络与工具风险检测
网络行为检测：检测请求内容中是否出现公网 IP 查询服务、可疑数据接收网站以及外部 URL。
工具调用风险检测: 检测 AI 是否可能执行危险的 Shell 命令，以及是否存在敏感数据外传行为。

1. 本地 LLM API 网关桌面应用
独立设计并实现本地大模型 API 网关桌面应用（Rust + Tauri 2 + React 19）。本机进程对外暴露 OpenAI 兼容接口，完成鉴权、选路、协议转换与用量记录；桌面窗口与无头 Web 管理端共用同一套 Rust 核心，可一键把网关地址、密钥写入 Codex / Claude Code / Gemini CLI 等客户端。

2. 多供应商协议统一转换
设计 Adaptor 层，将 OpenAI、Claude、Gemini、DeepSeek、Moonshot、通义千问、智谱、豆包、Ollama 等 9 家上游协议统一转为 OpenAI 兼容接口（Chat Completions、Responses、Messages、Embeddings）。下游始终按 OpenAI 形态接入，上游按渠道身份走原生协议，编解码在网关内完成。

3. 优先级 + 权重调度与故障转移
实现模型优先的路由调度器：先按模型命中与健康探测筛选候选，再按优先级分层，同层按权重随机抽样；原生协议组失败后自动切到协议转换组。单组最多 3 次、整请求最多 6 次尝试，无可用渠道时返回明确 503，避免打到错误上游。

4. 安全审计引擎
设计请求/响应双侧安全审计引擎：内置 25 条规则（凭证、敏感路径、Unicode 隐写、外联域名、危险命令、提示注入等），输出 Clean～Critical 六级风险与 0–100 综合评分。支持审计、警告、脱敏、阻断四种策略，Critical 可强制阻断，审计日志中的证据全程打码。

5. SSE 流式透传与 Token 用量统计
实现 SSE 流式透传：流式客户端只限制连接超时、不截断长生成；协议转换场景下把上游事件帧实时桥接回 OpenAI SSE。按 prompt / completion / cached / total 记录 Token，写入请求日志并累计到密钥配额；上游未返回 usage 时用 tiktoken 本地估算，保证计量不断档。

为什么 DaMaoAPI 选择在网关层做协议转换，而不是让下游应用各自适配不同供应商的 API 格式？

提示：考虑 N×M 的适配矩阵复杂度、维护成本、以及网关层统一转换后新增协议只需加转换层的扩展性优势。

Anthropic 的 SSE 流式事件与 OpenAI 的 SSE 流式事件在结构上有哪些关键差异？转换时最容易踩的坑是什么？

提示：OpenAI 是 delta.content 逐字推送，Anthropic 需要 message_start → content_block_start → content_block_delta → content_block_stop → message_delta → message_stop 完整生命周期。踩坑点：状态追踪（文本块何时关闭、tool_use 块的 index 管理）。

Responses API 和 Chat Completions API 的核心区别是什么？为什么 OpenAI 要推出 Responses API？

提示：Chat Completions 是对话式（messages 数组），Responses 是 Agent 式（input/output 扁平数组 + 内置工具）。Responses API 更适合 MCP 和 Agent 场景。

tool_use 和 tool_calls 的转换中，input（JSON 对象）和 arguments（JSON 字符串）的互转有什么需要注意的边界情况？

提示：serde_json::to_string 可能因特殊字符失败；serde_json::from_str 对不完整 JSON 会报错（流式场景下 arguments 是增量拼接的）。

extract_api_key 为什么优先检查 Authorization: Bearer 而不是 x-api-key？这种优先级选择有什么实际场景依据？

提示：有些应用（如 Cursor）发送 Anthropic 请求时也带 Bearer header。优先 Bearer 可以兼容这种"混合认证"场景，避免错误提取到空 key。




知识库的核心是四张表，形成 知识库 → 文档 → 切片 的层级关系：
kb_knowledge_bases (知识库)
    │  1:N
kb_documents (文档)
    │  1:N
kb_chunks (切片 + 向量)
    
kb_tasks (处理任务)



知识库的表结构为什么用 kb_knowledge_bases → kb_documents → kb_chunks 三层层级？两层（知识库 + 切片）是否足够？

提示：文档层提供了文件元信息（filename、file_type、file_size、content_hash）和状态追踪（pending→processing→ready→failed）。如果只有两层，这些信息要么丢失要么冗余存储在每个 chunk 中。三层结构还支持按文档管理（删除整个文档、重新索引单个文档）。

content_hash 用 SHA256 的作用是什么？为什么不是 MD5？

提示：SHA256 防止重复上传同一文件（hash 相同则跳过）。SHA256 比 MD5 抗碰撞更强，虽然在这个场景下 MD5 也够用，但 SHA256 是更安全的选择。代价是计算稍慢，但文档上传不是高频操作。

embedding 存储为 BLOB 而不是 JSON 字符串，为什么？具体节省多少空间？

提示：一个 1536 维的 f32 向量：BLOB = 1536×4 = 6144 bytes；JSON = [0.123456, -0.789012, ...] 约 1536×12 = 18432 bytes。BLOB 节省约 67% 空间。用 bincode 序列化更紧凑（无分隔符、无小数位冗余）。

tree-sitter 的符号感知分块 vs 固定大小分块，各自的适用场景是什么？如果代码文件没有 tree-sitter 支持（比如 Haskell），会怎样？

提示：代码文件必须用符号感知分块，否则函数被截断。非代码文件（txt/md/pdf）用固定大小分块即可。不支持的语言会 fallback 到 split_text——效果不如符号分块但仍可用。is_supported_language() 检查决定走哪条路径。

chunk_overlap=64 的重叠设计为什么重要？如果 overlap=0 会怎样？overlap 太大（比如 256）会有什么问题？

提示：overlap=0 时，跨分块的关键信息可能被截断（比如一个关键术语恰好出现在分块边界）。overlap 太大会增加冗余存储和检索噪声。64（约 chunk_size 的 12%）是经验值——足够保持语义连贯，又不至于过度冗余。





RAG：
原始文档 → 解析 → 切片 → Embedding → 向量/关键词检索 → LLM 回答
Wiki：
原始文档 → 解析 → LLM 提炼重组 → Markdown 页面
         → Wikilink 知识图谱 → 关键词检索 → LLM 回答
简单选择：

需要忠实查询原始合同、手册、代码：用 RAG。
需要自动整理成百科、操作指南、知识网络：用 Wiki。
更完整的做法是两者并用：RAG 负责原文证据，Wiki 负责结构化阅读和知识导航。


Wiki：
总体流程就是：
原始资料
→ 解析/OCR
→ LLM 提炼重组
→ Markdown Wiki 页面
→ 提取标签与 Wikilink（提取标签与 Wikilink”是从生成的 Markdown 页面中解析两类结构化信息。）
标签（Tags）
标签通常写在页面顶部的 Frontmatter 中：
---
title: 用户权限管理
tags:
  - 权限
  - 用户管理
  - 安全
---
系统会提取 权限、用户管理、安全 并保存到数据库，用于分类、筛选和管理页面。
Wikilink
Wikilink 是页面之间的内部链接，格式为：
用户需要先完成[[身份认证]]，然后根据[[角色权限模型]]进行授权。
系统会提取：
身份认证
角色权限模型
然后查找对应页面并建立知识图谱关系：
用户权限管理 → 身份认证
用户权限管理 → 角色权限模型
两者的区别：
标签表示“这个页面属于什么类别”。
Wikilink 表示“这个页面和哪些其他页面有关”。
→ 建立知识图谱
→ 关键词检索（关键词）
→ LLM 问答
⭐Wiki：Wiki 关键词检索是字符串包含匹配，不理解语义。例如搜索“怎样修改密码”，不一定能找到只写了“重置凭证”的页面；这种语义检索更适合 RAG 向量检索。




RAG：
原始文档 
→ 解析 
PDF：提取文字内容，必要时进行 OCR
Markdown/HTML：保留正文和标题结构
JSON/YAML：转换成可读文本
代码文件：保留函数、类、注释等内容
解析的目标是把不同格式统一转换成普通文本。
→ 切片 
大文档不能直接整体参与检索，因此需要拆成多个 Chunk。
10万字文档
按标题和段落切分
每个切片控制在一定 Token 范围
相邻切片保留部分重叠内容
重叠可以避免一句话或一个知识点恰好被切断。每个切片会记录：
所属文档
切片序号
原始内容
Token 数
标题、页码等元数据
切片大小过大，召回内容不够精确；过小则容易丢失上下文
→ Embedding 
每个切片发送给 Embedding 模型，转换成一组浮点数：
语义相似的文本，其向量空间距离通常更接近。
向量和切片内容一起保存，并建立 HNSW 索引来提升大规模检索速度。
用户提问时，同样使用该知识库配置的 Embedding 模型生成查询向量。因此，文档向量和查询向量的模型及维度必须一致。

→ 向量/关键词检索 
系统支持三种检索模式。
问题向量
→ HNSW 搜索
→ 余弦相似度计算
→ 返回语义最接近的 Top K 切片
适合“表达不同但含义相近”的问题。

→ 关键词检索：
问题分词
→ SQLite FTS5 全文检索
→ 找出包含关键词的切片
适合产品名、错误码、函数名、字段名等精确内容。

→ 混合检索：
向量检索 ──┐
            ├→ 去重 → RRF 排名融合 → Top K
关键词检索 ─┘
默认通过 RRF 根据两路排名进行融合。一个切片如果同时被语义和关键词检索命中，通常排名更高。
HNSW 索引不可用或过期时，系统会自动回退到全量向量扫描。
→ LLM 回答
系统读取最终召回的 Top K 切片，将它们和用户问题组合成提示词：
系统要求
+ 检索到的知识片段
+ 来源信息
+ 用户问题
然后发送给聊天模型。聊天模型不是凭空回答，而是根据检索上下文组织答案，并返回引用来源。


完整链路：
离线阶段：
文档 → 解析 → 切片 → Embedding → 保存向量/建立索引
在线阶段：
用户问题 → Embedding
         → 向量与关键词并行检索
         → 排名融合
         → 选取 Top K 上下文
         → LLM 生成答案及来源
RAG 的价值是让通用大模型能够使用本地或私有资料回答问题，同时减少模型幻觉，并且不需要重新训练模型。
